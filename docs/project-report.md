# 工程实践报告与答辩演示

## 1. 研究问题

模型离线训练成功不代表发布后长期稳定。候选版本可能产生服务错误、延迟升高或预测效果下降。若版本、监控和恢复机制彼此分离，出现异常后难以判断责任版本、恢复到正确模型或解释恢复过程。

本项目将版本登记、受控部署、可观察性、规则判断、回滚验证和审计统一成可重复验证的闭环。目标是工程机制的正确性与可复现性，不以 Iris 数据集精度作为算法创新。

## 2. 实现方法

训练阶段使用固定分层划分和随机种子，记录独立测试集指标与数据指纹。工件经原子写入后登记版本与 SHA-256，服务只加载登记且协议兼容的本机工件。稳定版本和候选版本分别管理；每次发布产生新的部署 ID。

运行阶段记录真实预测请求，以部署 ID 隔离指标。效果指标依赖独立标签反馈，避免将无标签数据漂移或服务错误错误称为准确率下降。控制器周期判断窗口指标，同时要求样本量、连续新证据与持续时间，减少低流量与瞬时抖动误触发。

恢复阶段校验稳定版本并验证实际服务指针，再原子保存部署与审计状态。失败保留原指针、停止自动循环并提供人工恢复路径。浏览器和 CLI 最后发起带标签的恢复请求，只有找到对应的一次自动回滚且恢复结果达标才生成通过报告。

## 3. 工程设计要点

1. **用部署 ID 而不只是版本号隔离指标**：同版本重发也不能继承上一次的异常窗口。
2. **稳定版本不等于上一版本**：候选发布不会覆盖稳定指针，晋升需额外验证。
3. **重复快照不算新证据**：同一批请求被重复轮询不会机械增加连续异常次数。
4. **回滚必须验证**：预检查与实际指针验证均成功才提交，不能把“发出切换命令”当成恢复。
5. **自动化失败有人工出口**：记录失败、停止重试，允许修复后回滚或指定可信新版本紧急恢复。
6. **实验不伪造闭环**：真实 HTTP 请求驱动记录，独立控制器触发回滚，报告核对真实事件与后续请求。

## 4. 实验设计与结果

- 场景 A：候选模型预测持续返回 503，错误率异常。
- 场景 B：每次预测额外增加 350ms，P95 延迟异常。
- 场景 C：将正常预测类别循环偏移，回传公开测试集真实标签后准确率异常。

全部场景先运行正常 v1/v2 流量，再注入故障；最后核验一次自动回滚、v1 运行、恢复后的无错误与带标签预测。实际数值、自动化测试覆盖和原始 JSON 记录见 [测试与实验报告](test-report.md)。这些是本机教学实验结果，不是生产 SLA。

## 5. 答辩演示脚本（约 8 分钟）

| 时间 | 演示内容 | 说明重点 |
| --- | --- | --- |
| 0–1 分钟 | 打开控制台总览 | 服务版本、稳定版本、窗口与心跳；缺数据不冒充健康 |
| 1–2 分钟 | 打开模型与发布页 | 两种模型、固定划分、评估指标、文件指纹和版本不可覆盖 |
| 2–4 分钟 | 运行场景 A，查看实时曲线 | 真实请求 → 异常计数 → 控制器判断 → 回滚 |
| 4–5 分钟 | 查看实验报告和事件日志 | 关联候选部署 ID、原因、故障恢复与回滚执行耗时 |
| 5–6 分钟 | 运行场景 B 或 C | 延迟与效果指标的区别；效果必须有真实标签 |
| 6–7 分钟 | 展示测试结果与 CI | 短暂异常、并发回滚、损坏工件、失败停止、人工恢复 |
| 7–8 分钟 | 说明边界与改进 | 单实例实现、生产多副本、外部宕机恢复与权限体系 |

## 6. 可说明的局限与拓展

本版是 CPU 即可运行的单实例教学系统。预测层与管理 API 同进程，无法在整个进程宕机时自行接收回滚请求；此类故障依赖外部进程管理。多副本切换需引入网关、共享控制平面与一致性机制；真正的生产效果反馈也需要可靠的标签来源。

后续可接入 MLflow/对象存储、外部模型评估、流量灰度、Kubernetes、多租户权限和自动再训练，但这些不作为本版完成项。当前未使用 PyTorch，以小型模型降低复现实验的硬件成本；运维机制不依赖具体模型训练框架。
